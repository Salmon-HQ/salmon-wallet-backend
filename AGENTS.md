# AGENTS.md instructions for salmon-api

Canonical rules for any AI agent or assistant working in this repo, regardless
of tool or vendor. Tool-specific files (`CLAUDE.md`, `.claude/`, `.codex/`)
only point back here — if they ever disagree with this file, this file wins.

## How to work here

- **Guidance is layered so you only load what you need**: this file holds the
  rules; each `src/*` folder has a nested `AGENTS.md` with folder-level detail
  (the closest one wins for its folder); `docs/` holds deep dives
  (`ARCHITECTURE.md`, `TESTING.md`, `DEPLOY.md`); skills under `.claude/skills/`
  and `.codex/skills/` hold on-demand workflows.
- **When in doubt, ask the human.** If placement, ownership, change scope, or
  contract impact is still genuinely ambiguous after reading the relevant
  `AGENTS.md` and docs, ask instead of guessing — a wrong guess on a public
  contract or folder boundary is expensive to unwind; a question is cheap.
- **Prefer a code graph if one is available.** If your environment exposes a
  code-graph / semantic-search / impact-analysis tool for this repo (e.g. a
  `.code-review-graph/graph.db` exists, or the harness provides an equivalent),
  use it for exploration and blast-radius checks — it is cheaper and more
  accurate than scanning files. Always verify findings against the actual
  source before acting; fall back to grep/glob/read when no such tool exists
  (a fork may not have one).

## Repo shape

This repo is a layered Express/Serverless backend organized as vertical slices per blockchain (`bitcoin/`, `solana/`, `ethereum/` skeleton), a `multichain/` slice for cross-chain endpoints (e.g. balance dispatch), and a `shared/` slice for cross-domain services that have no chain affinity.

`src/index.js` mounts each chain's routes via a loop over the `BLOCKCHAINS` constant, gated per mount by `multinetwork({ blockchains: [chain] })`. Adding a chain = append the constant + provide `src/routes/<chain>/index.js`. See the "Adding a new blockchain" section in `docs/ARCHITECTURE.md`.

Main flow:

- `src/routes` wires paths and middlewares
- `src/controllers` translates HTTP input/output
- `src/services` owns business flow and orchestration
- `src/repositories` and `src/infrastructure` talk to data sources or external providers
- `src/resources` shapes public API payloads

Reference doc:

- `docs/ARCHITECTURE.md` explains folder responsibilities in more detail

## Placement rules

One job per layer. This is what keeps changes local, providers replaceable, and
tests targeted — logic that leaks across layers couples chain slices together
and turns small edits into cross-cutting ones.

- Put new HTTP wiring in `routes`, not `controllers`.
- Keep controllers thin. If a controller starts coordinating providers or fallbacks, move that logic to a service.
- Put cross-provider orchestration, caching policy, and fallback policy in `services`.
- Put data access and source adapters in `repositories` unless the code is a shared technical client, in which case use `infrastructure`.
- Put response shaping and stable public payload mapping in `resources` — the resource layer is the public contract, so shape drift stays reviewable in one place.
- Keep `utils` for genuinely cross-domain helpers only. If a helper is Solana-only, keep it close to `src/*/solana` — chain-specific code in generic folders hides its real owner and blocks clean chain removal.

## Domain rules

- Solana-specific code belongs under the matching `src/{routes,controllers,services,repositories,resources}/solana` folder.
- Bitcoin-specific code belongs under the matching `src/{routes,controllers,services,resources}/bitcoin` folder.
- Ethereum is scaffolded but not active. Folders exist with AGENTS.md only; the router at `src/routes/ethereum/index.js` is empty so the chain-mount loop boots cleanly. Networks `ethereum-mainnet` / `ethereum-sepolia` are present in `src/constants/networks.js` but absent from every `network-capabilities-${stage}.enable` list, so the FE does not surface Ethereum.
- Cross-chain endpoints that dispatch on `locals.network.blockchain` (e.g. account balance) live under `src/{routes,controllers,services}/multichain`. The supported chains for each multichain endpoint are an explicit allowlist (e.g. `BALANCE_CHAINS` in `src/routes/multichain/account-router.js`) — adding a chain requires editing that allowlist. Cross-chain response shapes live under `src/resources/shared` (e.g. `account-balance-resource.js`); there is no `src/resources/multichain` because shapes do not need a dispatch layer.
- Cross-domain services with no chain affinity (coingecko, dapp, geo, network-catalog, network-capabilities, scam, trustwallet) live under `src/services/shared`. Their persistence partners live under `src/repositories/shared` and their public response shapes under `src/resources/shared`.
- Preserve public endpoint contracts unless the task explicitly allows breaking changes — deployed wallet clients parse these payloads, and a renamed field breaks them silently with no compile-time signal.
- Before removing backend surface, check active usage in the sibling frontend repo `../salmon-wallet-frontend` (when present) — it is the primary consumer, and searching it is the only reliable usage signal for an endpoint.
- Ethereum-related placeholders are intentional future surface, not dead code. Do not remove them unless the task explicitly asks for it.
- Contributing a Powerup: contributors never modify this repo. A read-only Powerup (its client calls the protocol's own endpoints) needs only a registry entry in `src/services/solana/powerups/registry.js` so it can be listed and switched off by id; a transaction-building Powerup needs that entry with `programIds` plus a build adapter a Salmon maintainer wrote and reviewed. The maintainer adds both, then flips the id on in the stage `powerups` block (`src/network-capabilities/network-capabilities-<stage>.js`). The registry is code, never remote or user-supplied.
- Triton One is the only Solana chain-data provider (RPC, DAS, enriched history via the local parser). There is no second provider and no fallback to one: a Triton failure reaches the caller. The resolver in `src/services/solana/providers` dispatches and logs. History keeps one degraded tier, the unclassified bare-RPC read (via `locals.network.config.nodeUrl`), which must remain functional.

## Signing boundary

The backend never receives a private key, a seed phrase or a signed
transaction, and never broadcasts on a user's behalf. A Powerup's backend
surface is: quote → unsigned transaction (or instructions) → the client
signs on the device → the client broadcasts to its own RPC → the backend
may read public status. `src/__tests__/signing-boundary.spec.js` enforces
it: every non-GET route must be in its allowlist with a reason (only routes
that BUILD an unsigned transaction qualify — NFT burn/transfer today), and
no controller may mention a signed-transaction body field. Every Powerup
is build-only (`GET /powerups/{id}/build`): the wallet's Apple
3.1.5(iii) answer rests on the backend never touching signed bytes.

## Error responses

- Error payloads use the envelope `{ error: '<snake_case_code>', error_description: '<human message>' }` with a meaningful HTTP status (e.g. `bad_request` 400, `nft_not_found` 404, `server_error` 500). The catch-all 404 and the final error middleware in `src/index.js` emit the same shape, so clients parse one error format everywhere — keep new endpoints on it.
- Reserve `500 server_error` for our own faults. Caller input is validated before the upstream call (400 `missing_parameter` / `invalid_parameter` / `bad_request`), our own back-pressure is 503 `upstream_rate_limited`, and an outcome we genuinely cannot determine says so (a 502 with a specific code) rather than claiming failure.
- Never answer 200 with an empty or degraded payload when the truth is that a provider failed. An empty balance, an empty NFT list or a catalog with everything disabled all read to the wallet as facts about the user's account. Let the failure surface.
- Upstream providers (CoinGecko, Esplora, RPC nodes) reject bad caller input with their own 4xx. `src/middlewares/error-handler.js` maps upstream 400/404/422 onto `bad_request`/`not_found`/`unprocessable_entity` and leaves every other upstream status as 500 — an upstream 401/429/5xx is our credentials or the provider being down, which the caller cannot act on. Do not re-map these per controller.
- Every outbound provider call goes through `providerCall` (`src/infrastructure/providers/provider-client.js`), which adds two 503s of our own: `upstream_unavailable` (that provider's circuit is open for this environment — it failed repeatedly and one probe per cooldown decides when it closes) and `request_budget_exhausted` (the request's 25 s budget is spent before the call could start). Both are deliberate fail-fast answers, never a fault to hide behind 500. Where a stale cached copy exists (the token catalog), it is served instead.
- Do not swallow unexpected errors in controllers — let them reach the final error middleware, which logs and responds 500 (or the mapped 4xx above). A silent catch hides the incident from logs and from the client. Any deliberate upstream pass-through must be documented in that slice's `AGENTS.md`.

## Testing rules

- Any new behavior should come with tests at the nearest meaningful layer.
- Before changing sensitive behavior, establish a small baseline test when practical.
- After changing behavior, rerun the targeted backend tests for the touched area.
- If the touched endpoint is consumed by `../salmon-wallet-frontend`, verify the most relevant frontend client or tests too.
- Prefer service/resource/controller tests over broad full-suite runs unless the change radius requires more.

### Unit vs integration naming (enforced by CI)

- All specs match `*.spec.js` (jest `testRegex`).
- A suite that hits real services (Redis, live provider APIs) MUST be named
  `*.integration.spec.js`. `npm run test:unit` excludes that pattern, and CI's
  `verify` job runs `test:unit` with no `.env`, no services, and no secrets —
  a misnamed integration suite either fails CI or, worse, silently makes CI
  depend on external services.
- `jest.setup.js` loads `.env` when present; unit tests must run
  hermetically without it. If a new module throws at import when an env var
  is missing, add a dummy there instead of making unit tests need a real
  `.env`.
- `npm run test:integration` runs `--runInBand` and needs a real `.env`.
- `npm run test:integration:local-validator` runs the `*.local-validator.integration.spec.js` suites against a `solana-test-validator` (Agave ≥ 4.2; install: https://docs.anza.xyz/cli/install) on `SOLANA_LOCAL_RPC_URL` (default `http://127.0.0.1:8899`). No secrets, no external network; skips when no validator answers. This is where behaviour that only a real node can prove lives (e.g. the bare-RPC path reading a real v1 transaction through the pinned `@solana/web3.js`). CI runs it on every PR via `.github/workflows/solana-validator.yml`, which also carries the nightly mainnet feature-status check that goes red when v1 activates.
- Full guide: `docs/TESTING.md`.

## Tooling

- Package manager: **npm**. `package-lock.json` is authoritative; install with `npm ci`. Do not add pnpm/yarn lockfiles — CI and the deploy workflow run npm, so a second lockfile silently drifts from what actually ships. (The sibling `../salmon-wallet-frontend` repo is a pnpm monorepo; that convention is that repo's, not this one's.)
- Runtime is Node 24 (`nodejs24.x` in `serverless.yml`; AWS deprecated `nodejs20.x` on 2026-04-30 and only ships runtimes for Active LTS releases, so a Node major moves only when Lambda lists it). Develop and test on Node 24 — `.nvmrc` pins it and `package.json#engines` enforces a `>=24` floor.
- Lint: `npm run linter` (ESLint with auto-fix) fixes locally; the PR gate runs `npm run lint:check` (zero warnings) — run it before finishing.
- Format: Prettier is enforced in CI (`npm run format:check`). Fix with `npm run format`.
- Merging is squash-only and gated by the `Protect main` ruleset (required checks, review, code scanning); an agent opens the PR and stops there — a repo admin merges with `gh pr merge <n> --squash --admin`, and the PR title becomes the commit on `main` (`docs/REPO-SETTINGS.md`).
- Every PR runs the deterministic gate in `.github/workflows/ci.yml` (format, lint, unit tests, serverless config smoke, hermetic Redis integration, conventional PR title, zizmor). Live-provider integration suites run in the nightly `integration-external.yml`, never in the PR gate.

## Dependencies

- This backend serves a wallet, so every dependency is supply-chain attack surface plus Lambda cold-start weight. Prefer, in order: existing code in the repo (`src/utils`, `src/infrastructure`, `packages/`), the Node stdlib, an already-installed dependency, and only then a new package — and justify any new package in the change description.
- Do not remove a dependency just because it looks unused without checking intent — some are kept deliberately for future surface (e.g. Ethereum). If intent is unclear, ask the human.

## Secrets

- Never commit secrets — not in code, config YAML, or docs. Prod secrets live only in AWS SSM Parameter Store (`/salmon-api/prod/*`); this keeps rotation out of git history and off forks. Every prod var in `config/env.prod.yml` is an `${ssm:...}` ref; five of them (`COINGECKO_API_KEY`, `TRITON_RPC_URL`, `TRITON_RPC_URL_DEVNET`, `GA4_MEASUREMENT_ID`, `GA4_API_SECRET`) carry an empty-string fallback, so a missing parameter deploys as unset rather than failing the deploy — check SSM, not the deploy log, when one of those features is silently off in prod.
- `.env` is gitignored, development-only, and intentionally diverges from prod (dev-safe values limit blast radius). Never treat it as a source of truth for prod values. Rotation flow: `docs/DEPLOY.md`.

## API contracts

These are the public-facing API contracts and their invariants. Changing the
behavior of any documented capability is a contract change — treat it as such
(check consumers, cover with tests, review):

- `solana-transaction-enrichment` — tx history shape, `_source` enum, provider routing (Triton only). Every item carries `memo` (the SPL Memo note, or null); a transaction that moves nothing and carries a memo is `type: 'memo'` (the Powerup `memo` build), whichever provider enriched it — the local parser reads the parsed text, a provider that sends only the raw instruction has its base58 data decoded. Triton's single-call `getTransactionsForAddress` is an optimisation, not a dependency: an endpoint that answers `-32601` pages by `getSignaturesForAddress` + batched `getTransaction` on Triton itself (`[TRITON_HISTORY_METHOD_MISSING]`, logged once) — there is no second provider. Token legs are hydrated per page from `solana-ft-service.getByMints` (catalog + DAS: `symbol`/`name`/`decimals`/`logo`, so `amount` is the correct base-unit integer; the bare-RPC reader reads the same fields off `list()`);; the parser resolves the owner of accounts opened inside the transaction from their `initializeAccount*` / ATA `create*` instruction, so a hop account that is closed again nets out instead of leaving a phantom leg, and any true residual of a pass-through token is listed after the tokens the user chose. NFT legs take their `logo` with the NFT list's precedence — the curated `nft-image-overrides.json` mirror first, then the asset image — so both screens load the same bytes — routers move SOL through wrapped-SOL accounts they open and close, so transfers show hops, not what the wallet ended up with. The Triton parser leaves `decimals` undefined on unchecked transfers so the catalog fills them (a `0` rendered USDC as an integer). Activity hides what the balance hides: an incoming transfer whose every leg is a fungible token without the catalog's `verified` tag is dropped from the page unless `includeSpam=true` — never a transaction the user paid for, never native SOL, never an NFT — and `meta.hidden` counts what the page dropped (enriched path only; the bare-RPC fallback lists everything). Every RPC reader (`parser/triton-rpc.js`, the bare-RPC path in `solana-transaction-service.js`) passes the integer `maxSupportedTransactionVersion: 1` (never the string `"1"`) so pages containing a v1 / 4096-byte transaction (SIMD-0296) are read instead of failing with `-32015`; `@solana/web3.js` is pinned to `1.99.0`, the first 1.x that accepts `version: 1` in a parsed response (read-only — the backend never builds v1). The npm `overrides` entry that makes the pin resolve is repo-wide, so Metaplex/umi and spl-token (NFT burn/transfer builders) run on it too. `npm run test:integration:local-validator` is what proves the pin still reads a real v1 transaction; run it when the pin moves. Backend readers do not surface compute/priority settings, so nothing here reads `transactionConfig`; `meta.fee` already includes the v1 priority fee
- `solana-source-catalog` — program-ID → source-name map, priority bands, source-add convention. The aggregator routers and the limit-order program (ids in `src/constants/solana-program-ids.js`) surface as `source: 'AGGREGATOR'` on the parser path, so a new router is one line in that list. The parser's `TOKEN_PROGRAM` / `TOKEN_2022_PROGRAM` / `ASSOCIATED_TOKEN_PROGRAM` sources surface as `SOLANA_PROGRAM_LIBRARY` (Helius's label for the same transfers), so the wallet sees one vocabulary whichever provider answered
- `solana-fungible-token-catalog` — `/ft/verified`, `/ft/search` shapes + fungibility filter. Sources: CoinGecko's Solana token list (snapshot ≤24 h per CoinGecko's terms; `coingeckoId` populated) ordered by market-cap rank. `tags` is two-level: `verified` = top-1000 Solana-ecosystem coins by market cap, `community` = every other listed token, `[]` = unlisted; the balance hides anything without `verified` unless `includeSpam=true` joined with Triton DAS metadata (`token-metadata-service`: symbol/name/decimals/logo, token program). Search is local over the catalog (exact symbol first); a bare mint address not in the catalog resolves on-chain and comes back unverified. USD prices (`_price`, `_usdBalance`, `_priceChange24h`) come from CoinGecko `simple/token_price/solana` and are absent, never 0, for unlisted mints. `/v1/networks` carries `attribution { text, url }` on `solana-mainnet` (CoinGecko requires it rendered).
- `capability-availability` — where a capability is offered is decided per request, never stored, from two signals: the caller's country (API Gateway's `sourceIp`, resolved through `packages/network-utils.resolveSourceIp` and the DB-IP Country Lite database bundled from `@ip-location-db/dbip-country-mmdb`; `src/availability/country-resolver.js`, `null` when unresolvable; addresses in the Ukrainian regions `UA-43` Crimea, `UA-40` Sevastopol, `UA-14` Donetsk, `UA-09` Luhansk, `UA-65` Kherson and `UA-23` Zaporizhzhia answer that ISO 3166-2 code instead of a country — ranges in `src/availability/region-ranges.json`, extracted from DB-IP City Lite by `scripts/build-region-ranges.mjs`, which wins over the country DB-IP gives, since DB-IP files much of Crimea under RU. The first four are embargoed (required unavailable on every row); Kherson and Zaporizhzhia are unavailable by default and may be opened by the table) and the platform (`X-Salmon-Platform: ios | android | extension`; missing or unknown → `ios`, the most restrictive; `src/availability/platform.js`). The availability table (`src/availability/availability-table.js`) maps capability × platform × country → a provider or unavailable: per capability `default`, `unavailable`, `providers` (name → countries) an optional `enabled: false` with a `reason` (`maintenance` | `deprecated`) that switches the capability off whatever the country, and optional `platforms.<platform>` overrides of those five keys, so a Powerup is taken down everywhere or on one platform by editing the parameter, without a release; it is read at runtime from SSM `AVAILABILITY_TABLE_PARAMETER` (5-minute cache per container, built-in default equal to the initial rows, keep-last-good on a read failure or an invalid document, logged `[AVAILABILITY_TABLE]`), and `AVAILABILITY_TABLE_JSON` / `AVAILABILITY_COUNTRY_OVERRIDE` force a table or a country on every stage except `prod`. Edit the parameter with `node scripts/availability-table.mjs` (dry-run by default; runs `validateTable` before writing, since the backend silently keeps the last good table on an invalid one). Validation refuses a document with an unknown provider, an unknown platform, a malformed country code, or any row that would make Jupiter serve a country in `JUPITER_PROHIBITED` (Jupiter's Terms of Use). `powerupGate(capability | 'param')` runs before every build: `404 not_found` when the row is switched off and `403 region_restricted` when the country is unavailable, both with no provider call, otherwise `res.locals.availability = { capability, platform, country, provider }` for the adapter choice; unresolvable country fails open on the default provider; logged `[POWERUP_GATE]` without the address. `GET /v1/solana-{env}/powerups/availability` (`Cache-Control: no-store`, never from the edge cache) answers `{ data: [{ id, enabled, reason?, provider? }] }` for every registered Powerup on the network (`swap` is a read-only registry entry, so the catalog, the stage switch and the gate agree on one id); it informs, the build route refuses. `/v1/networks.powerups` stays region-agnostic for 1.2.0 clients. DB-IP attribution ("IP Geolocation by DB-IP", CC BY 4.0) lives in `NOTICE` and must ship with any client that shows the country decision.
- `solana-swap-build` — `GET /ft/swap/build` runs behind the mainnet check and `powerupGate('swap')` (`capability-availability`: the row chooses the provider, `res.locals.availability.provider`; a row naming a provider without a configured credential → 503 `upstream_unavailable`, never a fallback to the other provider) and returns an UNSIGNED v0 transaction built from that provider's instructions — 0x (`zeroex-swap-provider.js`) or Jupiter (`jupiter-swap-provider.js`) under `src/services/solana/swap/`, adapters registered in `ADAPTERS` of `solana-swap-build-service.js` — fee payer = caller; shape in `src/resources/solana/solana-swap-build-resource.js` (`provider`/`providerDisplayName`/`attribution` are data, `salmonFee`/`routeFee` are objects, amounts are base-unit strings). Fee policy is server-side only (`SWAP_FEE_BPS` + `SWAP_FEE_ACCOUNT_OWNER`; recipient = the owner's ATA for the fee mint, or the wallet itself for native SOL). Providers do not create fee accounts, so the side is picked by what exists: output token first (`salmonFee.side = 'output'`), else input token (`'input'`), else the swap is built WITHOUT a fee and `[SWAP_FEE_SKIPPED]` is logged — never a 503, the user is not blocked by Salmon's ops gap; a build whose instructions never touch the recipient → 502 `provider_fee_mismatch`. `ZEROEX_DISABLED_SOURCES` (comma-separated DEX labels from `/enabled-sources`) excludes venues from routing. 0x 4xx errors are mapped by their `code` (`ZEROEX_ERROR_MAP` in `zeroex-swap-provider.js`): input codes → 400 `invalid_parameter`, token codes (`TOKEN_NOT_FOUND`, `TOKEN_HAS_UNSUPPORTED_EXTENSIONS`, `*_NOT_AUTHORIZED_FOR_TRADE`) → 422 `token_not_supported`, `TAKER_NOT_AUTHORIZED_FOR_TRADE` / any 403 → 403 `wallet_restricted`, Salmon-side config codes (`ALL_SOURCES_DISABLED`, `INCOMPLETE_SWAP_FEE`, …) → 500 `swap_misconfigured` + `[SWAP_MISCONFIGURED]` log, anything else → 404 `no_route`; `error_description` = 0x's text plus the code in parentheses; sustained 429 → 503 `upstream_rate_limited`. Priority fee: a compute-unit price is always prepended — `POWERUP_PRIORITY_FEE_MICROLAMPORTS` pins it (0 = none), unset = p75 of `getRecentPrioritizationFees` on the written accounts (zeros included) clamped to 1000–20000 µL/CU, paired with a compute-unit limit from `simulateTransaction` (+15%, 400000 fallback) so the fee is charged on real usage (`priorityFeeMicroLamports` / `computeUnitLimit` in the response). Intermediate token accounts a multi-hop route creates for the taker (a `createIdempotent` for a mint that is neither input nor output and does not exist yet — the taker's wrapped-SOL account counts as one, native SOL never stays in it) are closed at the end of the same transaction (`intermediate-account-cleanup.js`), refunding their rent to the taker — 0x, unlike aggregators that route through program-owned shared accounts, leaves them open (probed: a 1 USDC swap locked 17% of its output in an empty USD1 account); the close is simulated with the swap and dropped with a `[CLEANUP_SKIPPED]` log if the runtime rejects it, `intermediateAccountsClosed` in the response says how many were closed. Native SOL: the public contract keeps `SOL_ADDRESS` (`…112`) and the provider translates it to 0x's native sentinel `…111` (probed: `…112` would leave the user with wrapped SOL). `solana-mainnet` only (neither provider has a devnet). Compiled through the shared `powerups/unsigned-transaction-builder.js` with the simulation binding: a rejected simulation is refused, never a transaction the user signs to watch fail — `swap/simulation-errors.js` reads the failing program and code off the logs (Jupiter's IDL table, 0x Settler's probed 7001, SPL Token, System) into 422 `slippage_exceeded` / `insufficient_funds` / `insufficient_sol`, 404 `no_route`, 422 `token_not_supported`, 500 `swap_misconfigured` (logged), else the generic 422 `simulation_failed`; 503 `simulation_unavailable` when the RPC could not run it. After compilation the build refuses any top-level program outside the swap allowlist (502 `provider_program_mismatch`) and any second signer (502 `provider_signer_mismatch`); a Jupiter 200 whose shape is not the adapter's is 502 `provider_bad_response`; a 401/403 from either provider that is not 0x's own taker screening is 503 `upstream_unavailable` + `[SWAP_PROVIDER_AUTH]`, never `wallet_restricted` and never the raw error (it carries our key). The route is behind `txRateLimit`, and `validateSwapQuery` judges the request before the gate spends a screening. Sanctions: `sanctions:blocked` (a Redis set ops fills by hand with `SADD`, keyed like the rest by stage) refuses an address before any list and whether or not the SDN copy exists — it is how a provider's written block request (Jupiter licence §7.5) is honoured, and the daily refresh never touches it. The local Treasury copy is the only authoritative layer — missing, unreadable or older than seven days → 503, whatever TRM says; the refresh job throws on failure (Lambda Errors) and refuses a list below half the one held. The country database failing to open is 503 `upstream_unavailable` (`[COUNTRY_DB_UNAVAILABLE]`), never "no country"; an availability table that could not be refreshed for an hour reverts to the restrictive default; the validator refuses any row that routes an embargoed country. Every 0x answer is verified before it is read: the adapter sends `Accept-Signature` and a `Content-Digest` of its body, and `zeroex-response-signature.js` checks 0x's RFC 9421 Ed25519 signature over the status, the response body and the request's method, host, path, query and body digest against the pinned 0x key (`PINNED_KEYS`; a rotated key goes in `ZEROEX_SIGNING_KEYS` as JSON `{ keyid: x }` without a release) — unsigned, altered, stale (over 60 s) or foreign-key answers are 502 `provider_bad_response` + `[SWAP_PROVIDER_SIGNATURE]`, so a quote that did not come from 0x for exactly this order never becomes a transaction; Jupiter publishes no equivalent. Jupiter's own refusals are mapped by text (`JUPITER_ERROR_MAP` in `jupiter-swap-provider.js`, texts probed 2026-10-01): a pair it cannot route → 404 `no_route`; anything the controller already validates, a Zod shape error or a refused fee account → 500 `swap_misconfigured` + log.
- `community-powerups` — `/v1/networks` carries `powerups: Array<{ id, enabled, reason? }>` on EVERY network (`[]` when none or when the stage disables the network): registry (`src/services/solana/powerups/registry.js`) ∩ the stage's `powerups` block ∩ the entry's declared networks, `reason` only when `enabled: false` from the closed set `region` | `maintenance` | `deprecated` (any other value, or a non-boolean `enabled`, fails the config load and the catalog answers 503 `network_catalog_unavailable`), region-agnostic so the CDN copy is byte-identical everywhere. The catalog publishes only `{ id, enabled, reason? }`; contributor and endpoints are the registry's (reviewer's) record. The build route reads the stage block per request through the same predicate (`powerup-catalog-service.isOffered`), so the off switch is authoritative on deploy; `/v1/networks` is advisory behind CloudFront. `GET /v1/solana-{env}/powerups/{id}/build` returns an UNSIGNED v0 transaction (caller = fee payer, zero signatures) in one flat envelope — `provider` / `providerDisplayName` / `attribution`, `transaction`, `expiresAt`, `salmonFee: null`, `routeFee: null`, `contributor: { name, url } | null`, `priorityFeeMicroLamports`, `computeUnitLimit` — plus the adapter's typed display fields at the top level. Codes: 404 `not_found` for an unknown, disabled, read-only or undeclared-network id; 400 `missing_parameter` / `invalid_parameter` from the adapter before any upstream call (an adapter's own codes pass through only when listed in the entry's `errorCodes`); 502 `provider_program_mismatch` (an undeclared lookup table too), a message that needs any signature besides the caller's → 502 `provider_signer_mismatch` (logged `[POWERUP_PROGRAM_MISMATCH]` with the Powerup and program id) when the compiled message invokes an undeclared program or the adapter names a lookup table outside the entry's `lookupTables`; 422 `simulation_failed` when the runtime rejects it, 503 `simulation_unavailable` when the RPC could not simulate; the resilience 503s pass through unchanged. The honest guarantee: every top-level instruction, after lookup-table resolution, references a declared program or ComputeBudget; a declared program is trusted with everything it can CPI into; simulation proves the transaction executes, not what it invoked. The compile step (`src/services/solana/powerups/unsigned-transaction-builder.js`: priority fee, compute-unit limit, simulation, lookup tables, compiled program ids) is shared by every build. Adding a transaction-building Powerup is one registry entry (`programIds`, `lookupTables`, `errorCodes?`, `providerProfile?`) + one adapter + (if it calls a new upstream) one row in `src/infrastructure/providers/profiles.js`. `src/middlewares/powerup-gate.js` is the one seam for region gating (see `capability-availability`); the controller logs `[POWERUP_BUILD]` `{ id, network, outcome }`, never the IP. Deviation from spec 015: `salmonFee` is forced null on the generic route — fee legs land with the first Powerup that has one: the fee instruction is asserted present in the compiled message and a missing fee account is logged as an ops gap, never a 503, and the amount is never an adapter-reported figure. The registry's reference transaction-building Powerup is `memo` (one SPL Memo instruction), next to the deliberately non-compliant `broken-build` (emits an undeclared program, so it always answers 502); both live in `src/services/solana/powerups/adapters/` and are enabled on the `local` stage only, so the client's build path and its error states can be exercised against real unsigned transactions. Never enable `broken-build` on a shipping stage.
- `solana-nft-listing` — `/nft` owner-list flat backend shape; empty array when the owner has no NFTs; token-standard filtering. `pagination.hidden = { spam, fungible }` counts the items dropped from that page only (not cumulative): `spam` is what the blacklist / spam score hid (`0` when `includeSpam` is on), `fungible` is the DAS assets the resource rejected as fungible. `pagination.total` stays the provider's raw count, so a page can carry fewer than `limit` items. Spam hiding is a weighted score: each `spamReasons` code has a weight (table in the header of `src/services/solana/nft-spam-detector.js`), `spamScore` is their sum, and an item is dropped from the default listing when `spamScore >= SPAM_THRESHOLD` (2) — strong reasons hide alone, weak ones only in pairs. `duplicate_name` is wallet-level (the listing service counts names per page onto `locals`). The healthy-wallet fixtures under `src/services/solana/__tests__/fixtures/` pin that no legitimate NFT is newly hidden; re-tune against them, not by intuition. Token-2022 NFTs that the indexer lists without a name are named from the mint's own `tokenMetadata`, or from the account its `metadataPointer` names only when the mint is a `tokenGroupMember` of that account (joining a group needs the group's authority; a bare pointer does not), read in at most two batched `getMultipleParsedAccounts` calls that fail open (`[TOKEN2022_METADATA]`); an empty DAS record of the same mint is dropped. Every item carries `animation` (the document's `animation_url`, normalized like `media`, or null) and `frozen` (true when the holder's token account is frozen, as the Seeker Genesis Token's is)
- `solana-nft-burn` — token-standard routing (cNFT v1/v2, pNFT, edition, master); cNFT lookup-table fallback shape; error envelope. Fungible mints are refused (422) before any builder runs: `edition.isOriginal` derives from `supply.edition_nonce`, which is set on plenty of non-NFT mints, so decimals decide fungibility.
- `multichain-account-balance` — array-shape balance response with native/token branching for Bitcoin + Solana. Solana: read from the bare RPC only (`solana-rpc-balance-provider`: native + Token + Token-2022, every token account of a mint summed, in the balance item shape); Bitcoin's balance comes from Esplora (`bitcoin-balance-provider`). An RPC failure propagates — never an empty balance. `amount` is always the raw base-unit balance, the unit every transfer, fee and price calculation is denominated in. A Token-2022 mint whose Scaled UI Amount or Interest Bearing extension makes the displayed figure differ carries `uiAmount` beside it — a decimal string truncated at the mint's decimals, matching what the token program's own `AmountToUiAmount` returns — and clients render that instead of `amount / 10^decimals`; mints that scale 1:1 omit the key entirely. The balance reader does not report the multiplier, so `token-ui-amount-service` reads it from the mint, after the filters and only for mints the catalog marks `token-2022`, so a wallet of classic SPL tokens makes no extra request. `usdBalance` follows `uiAmount` when present because CoinGecko quotes these mints per displayed unit — scaled amount with scaled price, raw with raw, never crossed. A failed mint read serves the unscaled amount and logs, rather than failing the balance over one mint.
- `bitcoin-account-history` — canonical 9-bucket tx shape, fee attribution, full unspent set in one answer (422 `utxo_set_too_large` when the Esplora host refuses to enumerate it — mempool.space past 500 outputs). Source: the public Esplora API, mempool.space first and blockstream.info when it is down (`src/infrastructure/esplora-client.js`); history pages by the txid the previous page ended on, and transactions mined in the same block may come in either order. `script` on `/utxo` is the address's scriptPubKey, read off its history. `/utxo` items carry both the shipped `txId`/`outputIndex` and the `txid`/`vout` aliases the wallet's PSBT builder reads; records that cannot describe a spendable output are dropped rather than emitted with undefined fields. **Sending BTC does not work end to end yet**: the wallet derives P2PKH addresses (`m/44'/0'`), and a PSBT spending a P2PKH input needs `nonWitnessUtxo`, i.e. the full raw previous transaction. The backend does not serve raw transactions; the wallet reads each one from the same Esplora hosts (`GET /tx/{txid}/hex`). The Bitcoin slice is read-only: the wallet broadcasts its signed transaction directly to a public endpoint (mempool.space, blockstream fallback) and the backend never receives signed bytes — do not reintroduce a relay.
- `network-catalog` — `/v1/networks` shape, stage-derived `enabled` + `sections`. A misconfigured stage answers 503 `network_catalog_unavailable`, never a 200 whose networks are all disabled.
- `solana-stake-accounts` — `GET /v1/solana-{env}/account/:address/stakes` (`max-age=60`): every stake account whose staker (byte 12) or withdrawer (byte 44) is the address, deduplicated, `{ epoch, usdPrice | null, data: [{ address, lamports, delegatedLamports, voter, validator: { name, iconUrl } | null, activationEpoch, deactivationEpoch | null, state: activating | active | deactivating | inactive, rewards: [{ epoch, lamports, postBalance }] }] }`, lamports as strings, rewards for the last 5 completed epochs the stake earned in (newest first; an epoch the provider has no reward for is left out, each epoch cached 30 days). `validator` is what the operator published on chain (Config program validator-info, found by the vote account's identity, cached a day): `name` trimmed to 64 characters, `iconUrl` only when https, null when nothing is published — third-party text, never trusted. - `solana-skr-staking` — `GET /v1/solana-mainnet/skr/stake?owner=` (`max-age=60`; 404 `not_found` on any other network, 400 on a bad owner): the owner's positions in Solana Mobile's SKR staking program (`SKRskrmtL83pcL4YqLWt6iPefDqwXQWHSw9S9vz94BZ`, `UserStake` accounts found at byte 41, 169 bytes; layouts from the on-chain Anchor IDL), `{ mint, decimals: 6, sharePrice, cooldownSeconds, apy | null, usdPrice | null, liquid, totalStaked, positions: [{ address, staked, earned, guardian: { pool, name | null, commissionBps, active }, unstaking: { amount, withdrawableAt } | null, stakedSince | null, history: [{ at, earned }] }] }`, amounts as base-unit strings, times in epoch ms. `staked = shares × share_price / 10^9`, `earned = shares × (share_price − cost_basis) / 10^9` in integer arithmetic. Each request records the day's share price once (`skr_share_price:<UTC day>`, 400 days) and `history` is what the current shares earned between consecutive records since `stakedSince`; `apy` annualizes the widest span of records once it reaches 7 days. Guardian names come from a documented list (pools have no name on chain). `stakedSince` is the position's oldest indexed signature, null when the provider indexes none (Triton does not for some positions). `liquid` is the owner's SKR outside staking (its SKR token accounts, base units). `totalStaked` is everything staked in the program, `StakeConfig.total_shares × share_price / 10^9` (base units). `usdPrice` (both stake endpoints) is the CoinGecko quote of SKR / wrapped SOL through `getTokenPrices`, null when it cannot be had — a missing price never fails the read (`[STAKING_PRICE]`). Read-only (spec 021).
