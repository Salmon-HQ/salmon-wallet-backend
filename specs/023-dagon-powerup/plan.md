**Branch**: `feat/dev-93-dagon-powerup` (never merged; deployed to staging only) | **Date**: 2026-10-30 | **Spec**: [spec.md](spec.md) | Linear DEV-93

## Summary

`dagon` is one more transaction-building Powerup on the existing `GET /powerups/:id/build`: a registry entry, one adapter (four small files), two provider-profile rows, a stage flag, an availability row and an analytics enum value. The shared machinery changes in exactly two places: `compileUnsigned` also reports who the signers are, and the build service accepts extra signers only for an entry that declares fresh signers for the requested action, only on `solana-devnet`, and only when the compiled signer set is exactly `{caller} ∪ freshSigners`. `createInput` is a hand-encoded 91-byte gRPC-web call over the installed `axios`, so no dependency is added. Task zero proves on devnet, by sending real transactions, that Dagon's executor processes v0 transactions; only if it does not does the shared builder learn a legacy mode for `dagon` alone.

## Design, grounded in the code

1. **Signers in the compile result** — `compileUnsigned` already computes `requiredSignatures` from the simulated message (`unsigned-transaction-builder.js:270-276`). Add `signers: simulated.staticAccountKeys.slice(0, simulated.header.numRequiredSignatures).map((k) => k.toBase58())` to `base`. Additive: the Swap build reads only `requiredSignatures` and keeps its own single-signer check (`swap/solana-swap-build-service.js:407-408`), so Swap is untouched.
2. **Relaxed signer check** — in `powerup-build-service.js:110-131` compute
   `declared = entry.freshSigners?.[validated.params.action] ?? 0`;
   `fresh = declared > 0 && locals.network.id === 'solana-devnet' && validated.params.freshSigners?.length === declared ? validated.params.freshSigners : []`;
   then `assertSigners(id, built, [query.publicKey, ...fresh])` replaces `assertSingleSigner` (`:77-89`): pass iff `requiredSignatures === expected.length`, `signers[0] === publicKey`, and same set. Same error (`PowerupSignerMismatchError`, `powerup-errors.js:32-40`) and same log `{ powerup, requiredSignatures }`. For any entry without `freshSigners`, `expected = [publicKey]`, identical to today.
3. **Registry entry** — data-model.md "Registry entry". Program ids exported from `adapters/dagon/index.js`; `freshSigners` map (FR-002); `errorCodes: ['invalid_fresh_signers']` (pass-through at `powerup-build-service.js:58-62`).
4. **Stage flags** — `dagon: { enabled: true }` in the `powerups` block of `network-capabilities-staging.js:56-63` and `-local.js:55-67`; nothing in `prod`, `main`, `develop` (FR-003). `solana-devnet` is already enabled on staging (`network-capabilities-staging.js:24`), so the catalog predicate (`powerup-catalog-service.js:38-48`) lists it there and nowhere else.
5. **Availability row** — add to `DEFAULT_TABLE.capabilities` (`availability-table.js:112-126`), leaving `swap` untouched:
   ```js
   dagon: { enabled: false, reason: 'maintenance', platforms: { ios: { enabled: true, unavailable: EMBARGOED }, android: { enabled: true, unavailable: EMBARGOED } } },
   ```
   `rowsFor` (`:135-144`) gives iOS and Android `enabled: true` with the embargoed list and every other platform `enabled: false, reason: 'maintenance'`; it passes `validateRows` (`:146-200`, `dagon` is not in `REGULATED`, `default` null is allowed). Android is on for the hand-run QA on the Android emulator against the local backend (owner decision 2026-10-30). The gate (`middlewares/powerup-gate.js:34-77`) then answers 404 on the extension and 403 for an embargoed country; `provider` is null, so no sanctions screening (Jupiter-only, `availability-service.js:14`). The staging SSM copy gets the same row as JSON (quickstart §4), written only through `scripts/availability-table.mjs`.
6. **Analytics** — `'dagon'` appended to `POWERUPS` (`src/analytics/event-schema.js:52`).
7. **Profiles** (`profiles.js:23-93`): `'encrypt-executor': { tier: () => ({ rps: 5, burst: 10 }), timeoutMs: 5000, retry: RETRY_NONE, breaker: BREAKER_DEFAULT }` (no retry: a retried `createInput` can mint a second input; the wait loop is the retry); `'dagon-config': { tier: () => ({ rps: 1, burst: 5 }), timeoutMs: 3000, retry: RETRY_NONE, breaker: BREAKER_DEFAULT }`.
8. **`config.js`** — research R5. `getConfig(locals)` → accepted copy or throws `PowerupError(…, 503, 'dagon_config_unavailable')`; `axios.get(URL, { timeout, signal })` inside `providerCall('dagon-config', …, { locals })`.
9. **`executor.js`** — research R3–R4. `createInputs(values, authorized, config, locals)` runs the calls in parallel under `providerCall('encrypt-executor')`; maps failures to `executor_unavailable` / `executor_bad_response`. `waitCommitted(connection, inputs, reserves, locals)` polls `getMultipleAccountsInfo` every 750 ms while `remainingMs(locals) > 5000` (`request-deadline.js:33-36`); leftovers → `executor_pending` or `pool_unavailable`.
10. **`instructions.js`** — pure functions, one per row of research R6, plus `pda()` helpers (seeds from `GUIDE.md:85-96`), `readPcAccount`, `readCiphertextStatus`, `readReceipt` (R7). No I/O, so every byte is unit-tested against the kit.
11. **`index.js`** — `validate(query)` (data-model "Build request", sync, no I/O); `build(params, { locals, connection })`: load config → resolve sides → one `getMultipleAccountsInfo` for the chain state and fresh-signer freshness (R8) → 409s (data-model table) → executor inputs where the action needs them → wait → instructions. Returns `{ instructions, provider: { id: 'dagon', displayName: 'Dagon (devnet preview)', attribution: null }, display }`. Setup: create_deposit only when the payer's deposit PDA is absent, then InitializeAccount with `owner` (default caller), paid by the caller (`GUIDE.md:152-157, 226`). Send never onboards inside the transfer (spec OQ3, `pcSwap.ts:528-546`). Swap requires both pc-accounts (spec OQ2) and never prepends a deposit or init.

## Staging deploy (run by the agent after warning the owner)

Per `docs/DEPLOY.md:26-33`: staging is deployed by hand from the branch under test, never by CI. Owner decision: the agent runs both the SSM write and the deploy, warning the owner before each one, with AWS credentials exported from the owner's session (`eval "$(aws configure export-credentials --format env)"`, then `npm run serverless:deploy:staging`, which refreshes the country database and runs `refreshSanctionsJob`). This branch is based on `origin/staging` (`55015e3`), so the deploy carries everything partners test today. Order: SSM row first (an extra capability row is harmless to the code currently on staging, which validates it with the same `validateTable`), dry run first and `--execute` only after the warning; then the deploy, again after a warning; then the smoke in quickstart §4.3. No CI deploys staging; no prod tag is involved.

## Risks

- **The executor ignores v0** (research R1). Simulation would pass and every flow would look like an executor drop. Step 0 sends real transactions to rule it out before any code.
- **Shared staging stack.** Any staging deploy from `staging` between now and 2026-11-17 removes Dagon; partner Swap tests and the demo share one stack. The shared-code edits (steps 1–2) are additive and covered by the unchanged Swap, memo and gate suites.
- **Devnet RPC rate limits.** The build polls account state (~13 reads per swap). If `/salmon-api/staging/TRITON_RPC_URL_DEVNET` is empty, staging reads the public devnet RPC, which 429s under load (`GUIDE.md:68, 324`).
- **Executor latency and drops** (1–10 s commits, ~10% drops, `GUIDE.md:318, 326`) can push send/swap/unwrapBurn past the budget; the answer is a clean 503 `executor_pending` the device may retry, but SC-003's 9-of-10 depends on Dagon's infrastructure.
- **`devnet.json` on GitHub `main` is mutable.** A new epoch with the same programs is accepted without a deploy (intended); a program change is refused and Dagon goes 503 until a code change.
- **Plaintext amounts** go from the backend to a third-party executor (pre-alpha has no encryption, `GUIDE.md:38`); accepted by the spec (frontend disclosure).
- **Missing token account.** No Associated Token Account program is declared (FR-001), so a wallet without a mock-USDC/DOGE token account gets 422 on wrap; Dagon-funded wallets already have them.

## Open points

Points 1, 2, 5, 6, 9 and 10 keep their defaults and points 3 and 4 are decided (supervisor, 2026-10-30). Points 7 and 8 stay open for the owner.

1. **Legacy fallback** — default v0; step 2b only if step 0 shows the executor ignores v0.
2. **Input-wait reserve** — stop polling with 5 s of budget left for compile + simulate; tune after step 12 timings.
3. **Settling checks (decided: FR-029)** — swap and send refuse with 409 `balance_settling` when the input balance is pending (`data[99] != 1`) or never committed, as Dagon's reference does (`pcSwap.ts:525-527, 666-683`).
4. **unwrapDecrypt on a pending `burnedCt` (decided: FR-030)** — refuses with 409 `balance_settling`. A decryption requested before the burn commits may read the old value, and UnwrapComplete then closes the receipt and releases nothing (`lib.rs:770`), with no refund path (`GUIDE.md:341`).
5. **unwrapComplete before the decryption is posted** — leave it to simulation (422 `simulation_failed`); the device waits on the request account before asking. A dedicated 409 needs Encrypt's request-account layout, which the kit does not document.
6. **`minAmountOut = 0`** — refused (400), as the spec's amount rule says; the floor is not enforced on devnet anyway.
7. **Staging freeze** — no staging deploy from `staging` from 2026-11-13 to 2026-11-17; if one is unavoidable, merge `origin/staging` into this branch and redeploy it.
8. **Devnet RPC on staging** — the owner checks `/salmon-api/staging/TRITON_RPC_URL_DEVNET` before step 14 and sets it if empty.
9. **Docs** — no edits to `src/services/solana/AGENTS.md` or the root contract list on a never-merged branch (spec "Out of scope").
10. **Executor retries** — none (`RETRY_NONE`); a failed call answers 503 and the device retries the whole build.
