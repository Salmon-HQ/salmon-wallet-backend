# Research: Dagon Powerup (devnet preview)

Sources. `KIT` = Dagon's `inkwell-finance/pc-wallet-kit` (epoch 2, the copy reviewed for this plan): `GUIDE.md`, `devnet.json`, `reference/pcSwap.ts`, `reference/encryptRead.ts`, `vendor/encrypt/client/*`, `vendor/encrypt/examples/pc-token/{instructions.ts,lib.rs}`, `vendor/encrypt/examples/pc-swap/lib.rs`. The kit README says the vendored sources are "authoritative over the guide where they disagree". Backend paths are repo-relative; line numbers are at commit `46fda57`.

## R1. Does Dagon accept a v0 transaction? (FR-028, task zero)

- **Unknown, and simulation alone cannot settle it.** The programs never inspect the transaction version (no version check in `vendor/.../pc-token/lib.rs` or `pc-swap/lib.rs`; dispatch at pc-token `lib.rs:382-404` reads only instruction data). The risk is the off-chain executor: it reads Encrypt events from confirmed transactions, and Dagon's reference client only ever sends legacy (`GUIDE.md:117` "normal legacy `Transaction` (no versioned tx, no lookup tables)"). A v0 transaction could simulate and confirm while the executor never commits its outputs, which looks exactly like an executor drop (`GUIDE.md:326`).
- **Decision**: task zero proves both halves on devnet with a throwaway probe (`specs/023-dagon-powerup/probe/`, never under `src/`, because it signs with a QA keypair):
  1. Simulate one v0 message per instruction kind: create_deposit + InitializeAccount, Wrap, ViewBalance, Transfer, Swap, UnwrapBurn (UnwrapDecrypt/Complete need a live receipt; they ride on step 2).
  2. Send real v0 transactions from a Dagon-funded QA wallet: setup → wait balance ciphertext `data[99] == 1`; wrap 1.00 → wait digest change and status 1; swap 0.10 → wait both balances; one unwrap end to end. Pass = every output ciphertext commits within 90 s (the reference waiter's cap, `pcSwap.ts:493`).
  3. If step 2 fails for v0, repeat one wrap as legacy. Legacy commits and v0 does not → FR-028's fallback applies (plan step 2b). Both fail → executor outage, not a version problem; retry later.
- The probe also proves the hand-encoded gRPC-web `createInput` (R3) against the live executor before the adapter depends on it.
- **Alternatives**: simulate only (what FR-028 literally says) — rejected as insufficient for the executor half; build legacy from the start — rejected because it forks the shared builder for a guess.

## R2. Relaxing the single-signer rule (FR-009, FR-010)

- Today `assertSingleSigner` (`src/services/solana/powerups/powerup-build-service.js:77-89`) checks only `requiredSignatures === 1`; `compileUnsigned` reports that count (`unsigned-transaction-builder.js:275`) but not who the signers are.
- **Decision**: `compileUnsigned` also returns `signers`: the first `header.numRequiredSignatures` static account keys of the message it simulated (signers are always static keys, never lookup-table entries; index 0 is the fee payer). The build service replaces `assertSingleSigner` with `assertSigners(id, built, expected)`, where `expected = [publicKey, ...fresh]` and `fresh` is `validated.params.freshSigners` only when all of: `entry.freshSigners?.[validated.params.action]` is a positive number equal to `freshSigners.length`, and `locals.network.id === 'solana-devnet'`; otherwise `fresh = []`. The check passes only when `requiredSignatures === expected.length`, `signers[0] === publicKey`, and the two sets are equal. For every entry without `freshSigners` this reduces exactly to today's rule; the log line keeps `{ powerup, requiredSignatures }` and never prints keys (FR-025).
- **Alternatives**: a per-adapter `assertSigners` hook — rejected, an adapter could relax its own guard; trusting the adapter's count — rejected, the count is code in the registry (FR-002).

## R3. `createInput` over unary gRPC-web, server side

- No protobuf or gRPC package is installed (`package.json` dependencies: `axios`, `@solana/web3.js`, `@solana/spl-token`, `bs58`, no `@protobuf-ts/*`, no `@grpc/*`). The kit's client needs `@protobuf-ts/{runtime,runtime-rpc,grpcweb-transport}` (`vendor/encrypt/client/grpc-web.ts:20-22`).
- **Decision: no new dependency.** The one request and one response are tiny and fixed, so the adapter writes the bytes itself (~40 lines) and posts them with the installed `axios` inside `providerCall`:
  - Method path: `POST {executor}/encrypt.v1.EncryptService/CreateInput` (`encrypt_service.ts:459-462`). Headers `content-type: application/grpc-web+proto`, `accept: application/grpc-web+proto`, `x-grpc-web: 1`; `responseType: 'arraybuffer'`.
  - Request message (`encrypt_service.ts:257-276`, fields written only when non-default): `chain` (field 1) is `SOLANA = 0` and therefore omitted; `inputs` field 2 = one `EncryptedInput` { field 1 `ciphertext_bytes` = 17 bytes, field 2 `fhe_type` = 4 } (`encrypt_service.ts:187-193`); `proof` (field 3) empty, omitted; `authorized` field 4 = the 32-byte program id; `network_encryption_public_key` field 5 = 32 bytes. Bytes: `12 15 0a 11 <17> 10 04 22 20 <32> 2a 20 <32>` (91 bytes).
  - Plaintext value encoding (`grpc-web.ts:82-91`, `encryptValue`): `[fheType, value as 16-byte little-endian]`, 17 bytes. `fheType = devnet.json.fheTypeU64` (4).
  - gRPC-web framing (standard gRPC-web wire format, which `GrpcWebFetchTransport` speaks): each frame is 1 flag byte (`0x00` data, `0x80` trailers) + 4-byte big-endian length + payload. Request = one data frame. Response = a data frame holding `CreateInputResponse` (field 1 repeated `bytes ciphertext_identifiers`, `encrypt_service.ts:286-287, 316-320`) and a trailer frame `grpc-status: 0`; a trailers-only answer carries `grpc-status` in HTTP headers instead.
  - Result handling: exactly one 32-byte id → `PublicKey` (the reference refuses anything else, `pcSwap.ts:301-303`); zero, several, or a malformed body → 502 `executor_bad_response`; `grpc-status` 14 (UNAVAILABLE) or 4 (DEADLINE_EXCEEDED), a network error or HTTP 5xx → 503 `executor_unavailable` (the transport errors count toward the breaker); any other non-zero status → 502 `executor_bad_response`.
- **Alternatives**: `@protobuf-ts/*` (3 packages, supply-chain surface and cold start for 91 bytes); the npm `@encrypt.xyz/pre-alpha-solana-client`, which `GUIDE.md:110` calls "broken as published".

## R4. Waiting for executor inputs inside the 25 s budget (FR-022)

- The request budget is `res.locals.deadline` (`src/infrastructure/providers/request-deadline.js:24-36`); Dagon observes 1–10 s for `createInput` commits (`GUIDE.md:318`).
- **Decision**: after the `createInput` calls (in parallel, each under `providerCall('encrypt-executor')`), poll `connection.getMultipleAccountsInfo([...inputs, ...reserves])` every 750 ms (the reference interval, `pcSwap.ts:391`) until every account is ≥ 100 bytes with `data[99] === 1` (`GUIDE.md:101`). Stop polling when `remainingMs(locals) < 5000` (the compile + simulate reserve; `compileUnsigned` makes three RPC reads plus two simulations). Still pending → 503 `executor_pending` (an input) or 503 `pool_unavailable` (a pool reserve).
- **Alternatives**: return the transaction with pending inputs and let the device wait — rejected, a transaction sent while inputs are pending computes zero (`pcSwap.ts:707-713`) and the device would sign a no-op.

## R5. `devnet.json` at runtime (FR-012 – FR-015)

- **Decision**: fetch `https://raw.githubusercontent.com/inkwell-finance/pc-wallet-kit/main/devnet.json` with `axios` under `providerCall('dagon-config')`; cache the accepted copy in module memory for 5 minutes; on fetch failure or refusal keep the last good copy; with none, 503 `dagon_config_unavailable`. Accept only when: `cluster === 'devnet'`; `programs.pcToken`, `programs.pcSwap`, `programs.encrypt` equal the registry's pinned ids; `encryptGrpcUrl` parses as `https:` with hostname exactly `pre-alpha-dev-1.encrypt.ika-network.net`; `networkKeyHex` is 64 hex chars; `fheTypeU64` is an integer; `sides.USDC` and `sides.DOGE` each have valid base58 `splMint`, `pcMint`, `vault`, `vaultAta` and an integer `decimals`; `pool.sideA`/`sideB` name two distinct sides and every `pool.*` address is valid base58. Any `epoch` is accepted (spec open question 5).
- Byte offsets (`layout` block, `devnet.json:53-68`) are program layout, pinned with the program ids, so they are code constants and the remote copy of them is ignored. `rpcEndpoint` is ignored: devnet reads use the `solana-devnet` network config.
- The registry pins the Encrypt id too (spec open question 1 default): `4ebfzWdKnrnGseuQpezXdG8yCdHqwQ1SSBHD3bWArND8` (`devnet.json:12`, `GUIDE.md:75`).

## R7. Account layouts the adapter reads

- pc-account (`TokenAccount`, 202 bytes, owned by pc-token): mint `[0..32]`, owner `[32..64]`, balance ciphertext id `[64..96]` (`lib.rs:173-184`, `GUIDE.md:100`).
- Ciphertext (owned by Encrypt): digest `[2..34]`, status `[99]` (1 committed, 0 pending) (`GUIDE.md:101`).
- WithdrawalReceipt (203 bytes, owned by pc-token, PDA `[pc_receipt, burnedCt]`): owner `[0..32]`, amount `[32..40]`, pending_digest `[40..72]`, bump `[72]`, burned_ct `[73..105]`, vault `[105..137]`, pc_mint `[137..169]`, request `[169..201]`, decrypt_requested `[201]`, version `[202]` (`lib.rs:204-222`).
- Encrypt config (PDA `[encrypt_config]`): fee vault `[100..132]` (`GUIDE.md:102`).

## R8. Fresh-signer freshness

The programs refuse a fresh account that is not a signer, not empty, or not System-owned (`require_fresh`, `lib.rs:274-277`, error `0x105`). The adapter checks the same thing up front with one `getMultipleAccountsInfo(freshSigners)`: any existing account → 400 `invalid_fresh_signers` before any executor call (FR-007), so a reused key costs no executor input.

## R9. Where the work runs and how it reaches staging

- Staging is deployed by hand from the branch under test with the owner's credentials: `eval "$(aws configure export-credentials --format env)"` then `npm run serverless:deploy:staging` (`docs/DEPLOY.md:26-33`; script `package.json:24`, which also refreshes the country database and runs `refreshSanctionsJob`). Staging shares provider keys with prod (`docs/DEPLOY.md:35`).
- The staging availability table is SSM `/salmon-api/staging/AVAILABILITY_TABLE` (`config/env.staging.yml:50`), edited only through `scripts/availability-table.mjs --stage staging --file <table.json>` (dry-run by default, `--execute` writes and reads back; `scripts/availability-table.mjs:9-13, 30-35`), which runs the backend's own `validateTable`.
- This branch is based on `origin/staging` (`55015e3`), so a deploy from it carries everything staging runs today plus Dagon.
